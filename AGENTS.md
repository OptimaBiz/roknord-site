## Project Reality

Roknord is a Russian-language static B2B marketing site built with Astro 6 and plain CSS/JavaScript.

- Runtime: Node.js `>=22.12.0`.
- Package manager: npm; use the committed `package-lock.json`.
- Application source: `src/`.
- Static source assets: `public/`.
- Shared shell: `src/layouts/BaseLayout.astro`.
- Routes: file-based pages under `src/pages/`.
- Reusable UI: `src/components/`.
- Design system and global styles: `src/styles/`.
- Production build: `dist/` (ignored, generated by Astro).
- Deployment: production is built and uploaded to Timeweb with `npm run deploy:timeweb`; pushing `main` alone does not publish the site.
- `docs/` and `roknord-dist.zip` are legacy/generated publication artifacts, not implementation sources. Do not hand-edit or regenerate them unless the task explicitly names them.
- There is no database, API route, CMS, or client framework.
- The contact form submits to Formspree from `src/components/ContactForm.astro`. Do not send test submissions or change its endpoint without explicit authorization.
- The personal-account modal is UI-only. Do not imply that authentication or an account backend exists.

`README.md` is still based on the Astro starter and may be incomplete. For current structure, inspect the code; use `CODEMAP.md` only as an orientation aid and verify its claims against the repository.

## Copy And Legal Safety

Write in strict, evidence-driven Russian B2B language. Prefer concrete checks and deliverables over marketing adjectives. A useful section normally answers:

1. Что проверяем.
2. Почему это важно для процедуры.
3. Что получает заказчик.

Prefer formulations such as:

- независимый аудит готовности;
- карта рисков;
- проверка доказательной базы;
- подготовка к процедуре;
- анализ области аккредитации;
- выявление рисков до подачи;
- сопоставление документов и фактической практики;
- план корректирующих действий;
- проверка анкеты самообследования;
- анализ выборки дел;
- проверка связки «требование → процедура → запись → доказательство».

Avoid vague phrases such as `индивидуальный подход`, `опытные специалисты`, `качественно и в срок`, and `поможем пройти` unless concrete evidence immediately supports the claim.

Never use or paraphrase claims that imply guaranteed outcomes, special access, official status, or performing the regulator's function, including:

- гарантируем прохождение;
- гарантия прохождения;
- гарантия аккредитации;
- решим вопрос с Росаккредитацией;
- договоримся с экспертами;
- снимем замечания;
- закроем несоответствия;
- официальное заключение;
- официальное сопровождение;
- обеспечим положительное решение;
- аккредитация под ключ с гарантией;
- Не гарантия прохождения.

## News Article Canon

Статья `src/pages/postanovlenie-805-ohrana-truda-2026.md` и её опубликованная страница `/postanovlenie-805-ohrana-truda-2026/` являются обязательным эталоном для всех следующих материалов раздела `Новости`.

Новые статьи должны выглядеть и работать как части одной редакционной системы. Не проектируй для каждой публикации новую композицию. Между статьями разрешено менять только:

- рубрику и тематическую классификацию;
- URL и даты;
- заголовки, основной текст, таблицы, списки, FAQ и нормативные источники;
- уникальное тематическое изображение и его alt-текст;
- SEO- и Open Graph-тексты, относящиеся к конкретному материалу.

Не меняй для отдельной статьи общую сетку, типографику, размеры hero, положение изображения, логику оглавления, стили таблиц, отступы, цвета, акцент активного пункта, ширину текста или поведение на мобильных экранах. Любое улучшение общего оформления сначала вносится в общий `ArticleLayout.astro` или `article.css` и после этого должно одинаково применяться ко всем статьям.

- Текущее оглавление эталонной статьи задано в layout статически. Перед добавлением второй статьи параметризуй список оглавления через frontmatter или общий типизированный data contract, сохранив существующую разметку, scrollspy и визуальное поведение.

### Required Frontmatter Contract

Каждая статья должна передавать полный набор полей эталона:

```yaml
layout: ../layouts/ArticleLayout.astro
title: "SEO title"
description: "Meta description"
headline: "Видимый H1"
eyebrow: "Рубрика · подрубрика"
publishedDate: "YYYY-MM-DD"
publishedLabel: "Видимая дата"
updatedLabel: "Материал актуален на ..."
canonical: "https://roknord.ru/article-slug/"
ogTitle: "Open Graph title"
ogDescription: "Open Graph description"
image: "/images/news/article-slug.ext"
imageAlt: "Предметное описание изображения"
faq:
  - question: "Вопрос"
    answer: "Краткий самостоятельный ответ"
```

Правила полей:

- `title`, `description`, `ogTitle` и `ogDescription` должны описывать конкретный материал, а не раздел новостей в целом.
- `headline` — единственный H1 страницы.
- `canonical` — абсолютный production URL с завершающим `/`; он должен совпадать с фактическим маршрутом.
- `publishedDate` используется в машиночитаемых метаданных; видимые даты не должны ему противоречить.
- `image` — root-relative URL существующего файла из `public/images/news/`.
- `faq` обязан дословно соответствовать видимому FAQ в теле статьи. Не добавляй вопросы только в JSON-LD.

### Immutable Page Structure

Сохраняй следующий порядок блоков:

1. Общая шапка сайта.
2. Тёмный article hero:
   - breadcrumbs `Главная / Новости`;
   - рубрика (`eyebrow`);
   - один H1;
   - дата публикации и дата актуальности.
3. Двухколоночная editorial-сетка на desktop:
   - слева — липкое оглавление `В материале`;
   - справа — тело статьи.
4. В начале тела — одна крупная уникальная обложка 16:9.
5. После изображения — выделенный вводный абзац, который кратко отвечает, что изменилось и почему материал важен.
6. Краткий обзор ключевых изменений. Для сравнительного материала используй таблицу; для другого типа материала допустим компактный список, но позиция и роль блока сохраняются.
7. Основные тематические разделы H2 и объясняющие подразделы H3.
8. Практический раздел: что проверить, сделать или учесть читателю.
9. Итоговый раздел с кратким резюме без рекламного CTA.
10. Видимый блок `Частые вопросы`.
11. Блок первичных нормативных или официальных источников, когда тема на них основана.
12. Финальная строка актуальности материала.
13. Общий footer сайта.

Не вставляй внутрь экспертной статьи формы, рекламные баннеры, карточки услуг, CTA `оставить заявку`, всплывающие промо-блоки или искусственные перелинковочные блоки. Естественные внутренние ссылки допустимы только по смыслу текста.

### Headings, TOC And Scrollspy

- Каждый основной смысловой раздел статьи использует H2 с устойчивым латинским `id` в kebab-case.
- H3 используется только внутри ближайшего H2; не перескакивай через уровни заголовков.
- Левое оглавление содержит ссылки только на выбранные ключевые H2 и идёт в том же порядке, что и разделы статьи.
- Текст, `href` и фактический `id` каждого пункта должны быть синхронизированы.
- Не удаляй и не заменяй общий scrollspy: при прокрутке активная ссылка получает `aria-current="location"`, мятную левую линию и усиленный текст.
- Scrollspy должен учитывать липкую шапку, обновляться через `requestAnimationFrame` и не создавать отдельный обработчик для каждого раздела.
- При переходе по якорю заголовок не должен скрываться под header; сохраняй общий `scroll-margin-top`.
- На tablet/mobile оглавление остаётся доступным в потоке документа; не делай его горизонтальной каруселью и не скрывай без доступной альтернативы.

### Article Image Rules

- Для каждой статьи создавай или подбирай отдельное изображение, непосредственно связанное с темой. Не переиспользуй обложку другой новости.
- Предпочтительное соотношение сторон — 16:9; композиция должна выдерживать `object-fit: cover` и адаптивное кадрирование.
- Изображение должно быть нейтральным, реалистичным и соответствовать corporate assurance mood Рокнорд.
- Не используй логотипы третьих лиц, государственную символику, нечитаемые скриншоты документов, водяные знаки, надписи внутри изображения или визуальные обещания результата.
- Alt-текст описывает видимое действие или предмет, а не повторяет заголовок статьи и не содержит SEO-спам.
- Указывай реальные `width` и `height`, чтобы не создавать layout shift.
- Проверяй, что production URL изображения возвращает `200` и присутствует одновременно в HTML-карточке, `og:image` и `Article.image`.

### SEO And Structured Data

- Каждая статья обязана иметь уникальные title, description, canonical, `og:type="article"`, OG title, OG description, OG image и `article:published_time`.
- Сохраняй микроразметку `Article` с `headline`, `description`, `datePublished`, `dateModified`, `mainEntityOfPage`, `image`, `author` и `publisher`.
- Добавляй `FAQPage` только когда тот же FAQ полностью видим пользователю на странице.
- Ссылайся прежде всего на официальные первичные источники. Для нормативного материала проверяй номер, дату, дату вступления в силу и ссылку на официальный текст.
- Не создавай вымышленные нормативные факты, выводы, статистику, экспертные статусы или даты ради полноты статьи или SEO.

### Article Publication Checklist

Перед завершением каждой новой статьи:

1. Сравни страницу с эталоном `/postanovlenie-805-ohrana-truda-2026/` на desktop и mobile.
2. Проверь неизменность layout, классов, ритма, ширины текста и порядка структурных блоков.
3. Проверь breadcrumbs, единственный H1, иерархию H2/H3 и все якоря оглавления.
4. Прокрути статью и убедись, что каждый пункт scrollspy становится активным в соответствующем разделе.
5. Проверь горизонтальный scroll таблиц на mobile, отсутствие общего overflow и перекрытия липкой шапкой.
6. Проверь уникальное изображение, alt, реальные размеры и все ссылки на него в метатегах и JSON-LD.
7. Сопоставь видимый FAQ с массивом `faq` и микроразметкой `FAQPage`.
8. Проверь canonical, Open Graph, `Article`, дату публикации и строку актуальности в собранном HTML.
9. Проверь текст по правилам бренда, юридической безопасности и запретам на гарантии.
10. Запусти `npm run build` и проверь маршрут статьи и `/news/` без warnings и route failures.

Новая статья не считается готовой, если она требует собственных CSS-исключений, отличается по композиции от эталона, использует чужую обложку, имеет рассинхронизированное оглавление/FAQ или не представлена в каталоге `/news/`.

## Implementation Rules

- Prefer semantic HTML, Astro components, shared CSS tokens, and reusable utilities.
- Keep client-side code vanilla and minimal. Do not add a framework or heavy library for a local interaction.
- Keep content data near the component when that matches the existing pattern; do not introduce a CMS/data layer without a task requiring it.
- Preserve visible focus states, keyboard navigation, labels, landmarks, alt text, and reduced-motion behavior.
- Guard hover-specific behavior with an appropriate hover media query and keep touch behavior usable.
- Reuse assets from `public/`; do not edit generated copies under `docs/`.
- Use root-relative public URLs such as `/images/...` and `/pdf/...`.
- Do not expose secrets or add `.env` files to version control.
- Treat changes to the Formspree endpoint, consent/legal pages, analytics, external scripts, and deployment workflow as sensitive scope: change them only when explicitly requested and call them out in the handoff.

## Verification And Definition Of Done

For any application/frontend change:

1. Run `npm run build` from the repository root.
2. Review build output for warnings and route failures.
3. For layout or interaction changes, inspect the affected route at desktop and mobile widths when browser tooling is available.
4. Exercise affected keyboard interactions and check for obvious overflow, clipping, and focus regressions.
5. Search changed copy for forbidden claims and verify header/navigation canon when relevant.
6. Report the files changed, checks run, and any checks that could not be run.

Documentation-only changes do not require an Astro build unless they alter executable configuration. Do not regenerate `docs/`, archives, screenshots, or production artifacts as a side effect of verification.
